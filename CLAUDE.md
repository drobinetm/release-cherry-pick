# CLAUDE.md

This file gives Claude Code context on the `release-cherry-pick` repository.

## Project overview

`release-cherry-pick` is a Node.js CLI (built on Commander) that automates release cherry-picking and GitLab merge-request creation. It's designed to be installed/run as an **external tool from inside another git repo** (the "target" project being released) — this repo is the tool itself, not a project that gets released.

- Entry point / bin: `src/index.js` (exposes the `release-cherry-pick` command, `main` in `package.json`)
- Module system: CommonJS (`require`/`module.exports`), async/await throughout
- GitLab access is a direct REST client (`src/gitlab/client.js`, native `fetch`) authenticated with a Personal Access Token (scope `api`): `gitlab.token` in config, falling back to the `GITLAB_TOKEN` env var. The project path — and the API host when `gitlab.host` is empty — come from the `origin` remote URL via `parseRemoteUrl` (SCP-like SSH, `ssh://`, `http(s)://` with or without credentials; it checks for a `scheme://` before treating `host:path` as SCP syntax, since `https:` contains a colon too — that misparse used to send HTTPS remotes' requests to a wrong project path and 404). A configured `gitlab.host` wins (for SSH aliases) and goes through `normalizeGitlabHost`, since people paste project/page URLs there (e.g. `https://host/group/proj/-/project_members` — that put the API under the project path and 404'd): it drops everything from GitLab's `/-/` separator and the remote's project path suffix, but keeps any other path as a relative URL root (GitLab under `https://example.com/gitlab`), which `getProjectPathId(config)` then strips from the remote's path. The wizard applies the same normalization when the host is typed, and an http:// remote keeps http for the API. No `glab` dependency.

## Commands

- `release-cherry-pick release [-f <file> | -b <branches>]` → `runRelease()` in `src/workflow/release.js`. Resolves branches from a file, a CLI list, or interactively, then per branch: create release branch from staging → cherry-pick commits → (if `config.release.autoCreateMR`) push, select a reviewer, and create a GitLab MR via the REST API.
- `release-cherry-pick config [--init | --show]` → `setupWizard()` (Inquirer) or `loadConfig()`, both in `src/config/`.

## Architecture (`src/`)

- `cli/` — Commander program factory (`createProgram()`). Note: the actual commands are registered in `src/index.js`, not here — this module only sets name/description/version.
- `config/` — `defaults.js` (default config shape), `loader.js` (reads/writes the config **outside the project**, at `~/.release-cherry-pick/<project-key>.json` — `RELEASE_CHERRY_PICK_CONFIG_DIR` overrides the directory, which the sandbox uses to keep its config in `<sandbox>/config`. The key comes from the origin remote via `parseRemoteUrl` in `src/git/remote-url.js` (`host_group_proj`, the same for SSH and HTTPS clones), or the repo folder name + a hash of its path when there's no remote; it's resolved once per cwd with sync `git` calls, since load/save are sync. Saved with 0700/0600 modes; `loadConfig()` deep-merges the file over the defaults so options missing from older files are always present — except `git.branchPrefix`, which is a set picked as a whole: a saved one replaces the defaults (only `release` is filled in if missing), otherwise prefixes removed in the wizard would come back on every load — then runs `validateConfig` — pass `{ validate: false }` to skip, as the wizard does so it can repair a broken file), `setup.js` (Inquirer wizard: asks every option incl. `release.*`; source branch prefixes come from `promptSourcePrefixes`, a searchable multi-select of configured + detected (`countBranchesByPrefix` in `branch-selector.js`, reading existing refs without fetching; only prefixes on 2+ branches, since single ones are usually slashes inside names or typos) + common prefixes, with "+ Add another prefix…", saved keeping each prefix's existing key (new ones as the prefix without its slash), and the release prefix asked separately; when `autoCreateMR` is on it lists real project members via the REST client to pick `defaultReviewers`/`defaultAssignees`, falling back to typed usernames if there's no token or the call fails — it deliberately doesn't call `ensureAuthenticated`, which prompts for a token and saves the config mid-wizard, bypassing the review/cancel step), `validator.js` (`validateConfig`: type-checks the full merged config and throws one `ConfigError` listing every problem).
- `git/` — `branch-parser.js` (parses `*TASK-ID*: description` lines — no branch-name field), `branch-selector.js` (`getRemoteBranches` fetches then lists `feature/*`/`hotfix/*` remote branches, `getLocalBranches` the local ones; `getBranchCatalog(prefix, mode)` merges them into a `Map name → { local, remote }` — in `'local'` mode both, in `'remote'` mode origin only; `resolveBranchNameForTaskId(taskId, branches?)` finds the branch(es) matching a task ID, used by the `--file`/`-b` paths instead of guessing a name), `release-branch.js` (`buildReleaseBranchName`/`createReleaseBranch`/`pushBranch` — creates `release/<original-branch-name-with-known-prefix-stripped>` off staging; if the release branch already exists remotely *or locally* (exact name match) it does **not** auto-offer to delete/overwrite it — that's a destructive op on a shared branch — it just reports failure and leaves it for the user to resolve manually), `cherry-pick.js` (cherry-pick via `git.raw(['cherry-pick', ...])`; see "Commit selection" below), `release-status.js` (`ReleaseStatus` class — tracks per-branch `PROCEDE` / `NO PROCEDE` / `CONFLICT` / `SKIPPED` outcomes).
- `git/instance.js` — the only place `simple-git` is instantiated: `createGit()` passes `allowEnvironment: ['GIT_CONFIG_COUNT', 'GIT_CONFIG_KEY_0', 'GIT_CONFIG_VALUE_0']`. simple-git v4 strips ambient `GIT_*` variables from the git child process, which would silently drop the token header `git-auth.js` injects (and send every HTTPS push/pull back to git's interactive credential prompt). Note the option is spelled `allowEnvironment` in the code even though the v4 docs write `allowEnvoronment` — using the documented spelling does nothing. Every module must use `createGit()`, never `simpleGit()` directly.
- `gitlab/client.js` — REST client (native `fetch`, no shelling out): `ensureAuthenticated` (resolves PAT from `gitlab.token`/`GITLAB_TOKEN` or prompts interactively, validates via `GET /user`), `getProjectMembers` (`GET /projects/:id/members/all` with pagination), `getProjectLabels` (`GET /projects/:id/labels?include_ancestor_groups=true`, paginated), `createMergeRequest` (`POST /projects/:id/merge_requests`, maps reviewer usernames → `reviewer_ids`, sends `labels` as one comma-separated string). Project path is derived from the `origin` remote URL.
- `gitlab/` — `client.js` (REST API as above), `mr-creator.js` (orchestrates: fallback title/description from `config.release.mrTitleFormat` + commit list, tries AI content, then calls `gitlab.createMergeRequest` with squash/remove-source-branch flags `config.release.defaultAssignees`, which the client maps from usernames to `assignee_ids` like reviewers → `reviewer_ids`, and `config.release.defaultLabels`, picked in the wizard from the project's labels — `selectDefaultLabels` in `setup.js`, falling back to typed names without a token), `ai-description.js` (real Anthropic integration — see below), `reviewer-selector.js` (Inquirer checkbox over project members, pre-checking `config.release.defaultReviewers`, or legacy `defaultReviewerPattern` matches if that list is empty).
- `doc/` — `agents-generator.js` / `rpd-generator.js`: write `AGENTS.md` / `RPD.md` into the **target** project's root (prompt before overwrite).
- `report/` — `summary.js`: console + markdown release summaries (`PROCEDE`/`NO PROCEDE`/`CONFLICT`/`SKIPPED` status).
- `git/repo-state.js` — `captureStartingPoint()` (preflight run first thing in `runRelease`: refuses to start with uncommitted changes to tracked files or a cherry-pick in progress — untracked files are fine — and records the current branch, or commit if detached) and `restoreStartingPoint()` (run in a `finally` after the branch loop: aborts a leftover cherry-pick, checks the starting point back out, then deletes the release branches this run created that ended up empty — CONFLICT, SKIPPED or error, never pushed. PROCEDE branches, and any release branch that existed before the run, are never deleted). Note: `CHERRY_PICK_HEAD` is checked as a file, because simple-git's `raw()` doesn't reject when a git command fails without writing to stderr. `runInterruptible(work, cleanup)` wraps the branch loop so Ctrl+C also runs that cleanup: the first SIGINT sets `signal.interrupted` (the loop checks it between steps and stops; the branch in progress is discarded unless it was already pushed), then cleans up once the loop stops — or after a 2 s grace period if it's stuck on an Inquirer prompt, whose promise never settles — and exits 130; a second Ctrl+C exits immediately. While it runs it also shims `process.kill(process.pid, 'SIGINT')` (what Inquirer calls on Ctrl+C in a prompt) into a plain `SIGINT` event, because on Windows `process.kill` terminates the process unconditionally, skipping every handler.
- `workflow/release.js` — the main orchestrator (`runRelease`) tying config, GitLab token preflight, branch resolution, cherry-picking, reviewer selection, MR creation, and reporting together.
- `utils/` — `errors.js` (`AppError` base, subclassed by `ConfigError`/`GitError`/`GitLabError`), `logger.js` (chalk-based colored logger: `info/warn/error/success/header/table`).

## Source branch lookup: local first

`config.git.branchSource` (default `'local'`, overridable per run with `--local`/`--remote`) decides where source branches are looked up. `runRelease` builds one catalog up front (`getBranchCatalog`) and every input path (file, `-b`, saved/interactive) resolves against it; anything not in it gets a `missingReason` and is reported `NO PROCEDE` (no more guessing a `feature/<id>` name that later fails in `git log`). Then `attachSourceRefs` sets each `branchInfo.sourceRef`: the local branch name when it exists locally in local mode, `origin/<branch>` otherwise. If the local branch is behind its `origin` copy it asks which one to release (default origin's) — otherwise commits pushed by a teammate would be silently left out. `sourceRef` is what `getCommitsToCherryPick`/`findLooseTaskCommits`/`orderCommitsByHistory` read from (their default is still `origin/<branch>`); the base is always `origin/<staging>`. The MR is opened from the pushed release branch, so a local-only source branch never needs pushing — except with `--list-branches`, which opens the MR from the source branch itself and therefore forces `'remote'` (`--local -l` is a `ConfigError`).

## Commit selection for cherry-pick (important, found via real-world testing)

`getCommitsToCherryPick(sourceBranch, taskId, baseBranch)` in `src/git/cherry-pick.js` does **not** diff `sourceBranch` against `baseBranch` as a plain range. That was the original approach and it breaks in practice: real branches are often cut from a much older/different base than current `staging` (e.g. `develop` synced only periodically), so `staging..branch` can pull in hundreds of unrelated commits, or (if the branch's work already landed elsewhere) `develop..branch` can show zero commits even though the fix is genuinely still missing from `staging`. Verified against a real PROBROKER branch: `staging..hotfix/PB-I3245-...` returned 606 unrelated commits.

Instead it matches commits by the team's own `"[TASK-ID] description"` commit message convention (used consistently — 234/13687 commits in one real repo), restricted to commits not already reachable from `baseBranch`: `git log origin/<branch> --grep='^\[TASK-ID\]' --extended-regexp --regexp-ignore-case --not origin/<baseBranch> --reverse`. This reliably isolates just this task's own commit(s) regardless of the branch's real topology. `runRelease` passes `branchInfo.taskId` as the match key. Git's `--grep` matches any line of the message, so results are then filtered to commits tagged in the **title** (simple-git's `message` is the subject).

Commits that mention the task ID without following the convention (`PB-700: fix`, `(PB-700) fix`, or the tag only in the body) would otherwise be left out of the release silently. `findLooseTaskCommits` finds them among the branch's commits not on `baseBranch` (excluding merges, titles tagged for another task, and IDs that merely start the same, e.g. PB-7000). `selectTaskCommits` in `release.js` lists them, asks whether to include them (default no; `orderCommitsByHistory` keeps branch order when mixing), and records the outcome as a note (`ReleaseStatus.addNote`) shown under the task in the console summary and `release-summary.md`. Commits with no ID at all aren't reported: they can't be told apart from unrelated history on branches cut from an old base.

Those can be added **by hash**: in brackets after an entry of `-b` (`"PB-123[abc1234,+def5678],PB-124"` — `parseBranchEntries` in `branch-parser.js` splits on commas outside brackets only and rejects unbalanced/empty brackets or non-hex hashes before anything runs; it replaced the plain `split(',')`), `--commits PB-123=abc1234,...` (repeatable; `parseCommitSpecs` in `branch-parser.js` rejects malformed values before anything runs), a trailing `[+abc1234, ...]` on the task-file line (`parseBranchLine` → `extraCommits`; only a list made entirely of `+hex` counts, so ordinary bracketed text stays in the description), or — when a task has no commits at all — a prompt in `selectTaskCommits` (`askForCommitHashes`). All sources merge into `branchInfo.extraHashes` (`attachExtraHashes` warns about `--commits` task IDs not in the release). `resolveExtraCommits` (`cherry-pick.js`) validates them: unknown/ambiguous hashes and merge commits throw (→ `NO PROCEDE`); commits already reachable from `origin/<staging>` are skipped with a note; commits not reachable from the task's `sourceRef` need confirmation (default no). Reachability uses an empty `rev-list ref..commit` range, **not** `merge-base --is-ancestor`, whose answer is only the exit code — which `raw()` doesn't surface. `orderCommitsByHistory` sorts commits not on the branch last. Because of this validation, `runRelease` now calls `selectTaskCommits` **before** `createReleaseBranch`, so a bad hash never leaves a branch behind. Extra commits (`--commits` or `-b` brackets) are ignored, with a warning, under `--list-branches`. In PowerShell, comma lists passed to the npm `.ps1` shim must be quoted: unquoted `a,b` becomes an array that reaches node as `a b`.

A cherry-pick can also come back **empty** (git: "The previous cherry-pick is now empty...") when the commit's net change is already present in the target tree (e.g. the same fix landed a different way) — this is not a real conflict, even though git's own message contains the word "conflict" in passing. `cherry-pick.js` distinguishes this from a real conflict by checking `git status().conflicted` — if there are no actually-conflicted files, it treats it as already-applied, runs `git cherry-pick --skip`, and keeps going (does not abort the branch). `runRelease` checks `cherryPickResult.commitsCherryPicked === 0` after a "success" and marks the branch `SKIPPED` (no push, no MR — nothing to release) rather than `PROCEDE`.

## AI-generated MR content

`src/gitlab/ai-description.js` calls the Anthropic Messages API (`@anthropic-ai/sdk`) to draft the MR title and description from the branch's commits, gated on `config.ai.enabled`. API key resolves from `config.ai.apiKey`, falling back to the `ANTHROPIC_API_KEY` env var. Default model: `config.ai.model` (default `claude-haiku-4-5-20251001`). On any failure (disabled, no key, API error, bad JSON) it returns `null` and `mr-creator.js` falls back to the static `config.release.mrTitleFormat` + commit-list template.

## Conventions

- Always log via `src/utils/logger.js`, not raw `console.log` (a couple of `console.log(JSON.stringify(...))` calls exist only for `config --show`, which prints a copy with `gitlab.token` and `ai.apiKey` masked via `maskSecret` in `src/utils/secrets.js`).
- Secret prompts (GitLab token, AI API key) must use Inquirer `type: 'password'` with `mask: '*'` — in inquirer 8, `mask` on a `type: 'input'` prompt is silently ignored and the secret is echoed in clear.
- AI defaults: `ai.provider`/`ai.model`/`ai.baseURL` default to `''` on purpose — `ensureAiSettings` (in `setup.js`) prompts for provider/model at release time when AI is enabled and they're missing, and an empty `baseURL` lets `resolveBaseURL` pick each provider's own endpoint (a non-empty `config.ai.baseURL` wins for *any* provider).
- Errors: throw the appropriate `AppError` subclass; top-level handlers in `src/index.js` catch, log `error.message`, and `process.exit(1)`.
- Config is plaintext JSON kept in the developer's home directory (see `loader.js` above), never in the target repo, so its secrets can't be committed by accident — no `.gitignore` handling is needed or done. It holds `gitlab.token` (PAT with `api` scope; can also come from `GITLAB_TOKEN` env) and optional `gitlab.host`; the project id is resolved from the `origin` remote, not stored.
- Branch naming: original branches are `feature/*`/`hotfix/*`; release branches are `release/<original-name-with-known-prefix-stripped>` (e.g. `feature/PB-123-list-user` → `release/PB-123-list-user`) via `buildReleaseBranchName` in `src/git/release-branch.js`. Prefixes configurable via `git.branchPrefix` and honored everywhere: the release prefix names the release branch, and every non-release prefix (`getSourcePrefixes` in `src/git/branch-selector.js`, falling back to the defaults if none configured) defines which remote branches are listed/matched by task ID. Staging branch defaults to `staging`.
- Task IDs: uppercase alphanumeric with hyphen, e.g. `PB-I3217` (regex in `src/git/branch-parser.js`).
- MR titles: `config.release.mrTitleFormat` (default `[{taskId}] {description}`), used as the fallback when AI generation is off/fails; AI-generated titles are instructed to keep the `[{taskId}] ` prefix.
- MR options: `config.release.mrSquash` / `config.release.mrRemoveSourceBranch` both default `true` (GitLab's squash + delete-source-branch checkboxes), sent as `squash` / `remove_source_branch` on `POST /projects/:id/merge_requests`.
- Reviewer: `config.release.defaultReviewerPattern` (default `'^che(i|y)ner$'`) is matched case-insensitively against real project members (`gitlab.getProjectMembers()`) to preselect a default in the per-branch reviewer prompt; selected usernames are mapped to numeric `reviewer_ids` before the MR is created.
- Domain terminology is Spanish-influenced (`PROCEDE`/`NO PROCEDE`/`CONFLICT`/`SKIPPED` status, `'es-ES'` locale in generated `RPD.md`), reflecting the team's locale.
- `simple-git@4.0.2` (upgraded from `^3.36.0` for the critical advisories fixed in 4.0.2) has **no `cherryPick()` method** — cherry-pick operations must go through `git.raw(['cherry-pick', ...])`, not a hypothetical `git.cherryPick(...)`. v4 also removed the default export (`const { simpleGit } = require('simple-git')` returns an object, not a function) and blocks abbreviated long-form options (`--conf=` → `GitConfigurationError`), so keep passing full option names — all of this suite's `raw()` args are already canonical.

## Build / test

- `npm start` — runs the CLI (`node src/index.js`).
- `npm test` — placeholder only (`echo "Tests not yet implemented"`), not a real test runner.
- `node test-e2e.js` — manual smoke script (no assertions) exercising branch parsing, config defaults, `ReleaseStatus`, markdown summary, and doc generation. Not wired to `npm test`.
- `npm run sandbox:create` / `npm run sandbox:run -- [-b <list> | -f tasks.txt]` — synthetic disposable sandbox (`scripts/sandbox/`): a local bare `origin` + clone in `$TMPDIR/release-cherry-pick-sandbox` with branches covering each scenario (normal, untagged commit, conflict, already-applied → `SKIPPED`, duplicate task ID, no task ID, local-only `PB-600`, local-behind-origin `PB-610`, untagged-only `PB-700` for `--commits`), config `autoCreateMR: false` (no push/GitLab API). `run-release.js` auto-answers Inquirer prompts; `npm run sandbox:config` runs the setup wizard the same way. Shared `harness.js` flags: `--fake-gitlab` (intercepts `fetch()` to `/api/v4` and sets a fake `GITLAB_TOKEN`, so the real `src/gitlab/client.js` runs against a fake — fixed members and labels, `POST merge_requests` prints its body) and auto-answers the searchable `autocomplete`/`checkbox-plus` prompts from `src/utils/prompts.js` too and `--answer name=value` (force a prompt's answer). Use this to validate git-flow changes before touching any real repo.
- `npm run lint` / `npm run lint:fix` — ESLint (flat config, `eslint.config.js`, `eslint:recommended` + CommonJS/Node globals). A Husky `pre-commit` hook (`.husky/pre-commit`) runs `lint-staged` (`*.js` → `eslint --fix`) automatically on every commit, only against staged files. Hooks are installed with `npm run setup` (runs `husky` once after cloning) — there is deliberately **no `prepare` lifecycle script**, so nothing hook-related ships in the published package (`npm pack`/`npm publish` never runs it either). No Prettier config present (despite AGENTS.md-generated output claiming ESLint conventions for target projects — that doc is about *target* projects, not this repo).
- `npm run test:package` — end-to-end test of the **published npm artifact**, not the checkout (`scripts/sandbox/test-package.js`; flags `--version <v>`, `--sandbox <dir>`, `--keep`). Phase 1 downloads the registry tarball and checks `dist.integrity`, file list (no `.env`/keys/`.git`, no `preinstall`/`install`/`postinstall` scripts), MIT license vs `LICENSE`, `type: 'password'`+`mask: '*'` on every secret prompt, and scans shipped files for secrets (documentary placeholders excluded). Phase 2 runs a real `npm install` of the tarball into a sandbox prefix, exercises the bin (`--version`, `--help`, `config --show` with `RELEASE_CHERRY_PICK_CONFIG_DIR`) asserting the real `~/.release-cherry-pick` stays untouched, plus `npm audit`. Phase 3 runs the mutated flow twice via `run-release.js --tool <installed-copy>`: `autoCreateMR: false` (nothing pushed; only PROCEDE branches kept locally; exactly the tagged commits picked, staging untouched) and `autoCreateMR: true` against `--fake-gitlab` (push + MR body asserted) — the sandbox's origin is rewritten to `https://gitlab.example.com/sandbox/project.git` with `url.*.insteadOf` pointing back at the local bare repo, and a `git` shim on PATH returns the raw URL for `git remote get-url` (which would otherwise apply insteadOf and break `parseRemoteUrl`); the config must be written with that same shim in PATH or its project key won't match. Phase 4 writes a config containing fake PAT/AI key and asserts `0600`/`0700` modes, no raw secret in console output, `release-summary.md` or git metadata, and masked `config --show`. Phase 5 runs against the local checkout: simple-git must resolve to ≥4.0.2 (the version that fixes the criticals), and a probe proves the `GIT_CONFIG_*` token header reaches git through `createGit()` while a plain `simpleGit()` instance strips it (the allow-list is load-bearing). Currently: **82/82 checks, 0 warnings** against the published `1.0.3` (deterministic tarball via `files: ["src"]`, no `prepare` in shipped metadata, `npm audit` clean on simple-git ^4.0.2).
- The npm tarball is scoped by the `files` field in package.json (`["src"]` only — `README`/`LICENSE`/`package.json` are always included; 31 files total). There is deliberately **no `.npmignore`** and there never was one: without the `files` field npm packs the whole working tree, which is how `1.0.1` shipped `openspec/`, `.atl/`, `.github/`, `.husky/`, `CLAUDE.md`, `scripts/` and `tests/`. Never widen `files` with dev/test/agent-state paths — `npm run test:package` phase 1 warns on non-runtime files and fails on secrets found outside the runtime allowlist.
- Releasing to npm is automated by `.github/workflows/publish.yml`, triggered by pushing a `v*` tag (not by pushes to `main`: npm versions are immutable, so republishing the same version fails, and not every commit is a release). Flow: `npm version <patch|minor|major>` → `git push --follow-tags`. The workflow fails if the tag doesn't match `package.json` version, then runs lint, `npm pack --dry-run` and `npm publish --provenance`, then creates the GitHub Release for the tag (`gh release create --generate-notes`, needs `contents: write`). Auth is npm Trusted Publishing (OIDC, no `NPM_TOKEN`): the package must have a Trusted Publisher configured on npmjs.com (GitHub Actions, owner `drobinetm`, repo `release-cherry-pick`, workflow `publish.yml`, no environment, **"Allow `npm publish`" ticked** — otherwise `npm publish` fails with `E403 OIDC permission denied`), and `repository.url` in `package.json` must match the GitHub repo or provenance is rejected.
- The GitLab REST paths used in `src/gitlab/client.js` (`GET /user`, `GET /projects/:id/members/all`, `POST /projects/:id/merge_requests`, `PRIVATE-TOKEN` auth header, `reviewer_ids`) follow the public GitLab API docs but were **not** live-verified against a real instance from this environment (no token configured here). Re-verify with a test project if MR creation misbehaves. Exception: `GET /projects/:id/labels` *was* verified read-only against the real PROBROKER project (16 labels listed); sending `labels` on MR creation has only been exercised against `--fake-gitlab`.
- The branch-creation, commit-selection, and empty-cherry-pick logic (everything in "Commit selection for cherry-pick" above) *was* validated against real data: a disposable local mirror clone of an actual production repo (PROBROKER, `gitlab.ingeniuscuba.com`), never pushed to or otherwise touching the real remote. MR creation/reviewer-listing/AI generation were not exercised this way (no real GitLab MR was created, no Anthropic key configured).
